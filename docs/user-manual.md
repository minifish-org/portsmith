# Portsmith 使用说明书：自动迁移 Pith

你现在操作的是整个迁移计划。**启动一个命令，Portsmith 自动选模块、生成、验证、修复、集成并逐模块提交。** 中断后重跑同一命令继续，无需逐个填写 unit、judge、out 或 task。

## 1. 现在准备好了什么

- Pith 的 `migration/plan.json`：固定 Pi 来源、9 个任务及其依赖。
- `migration/API.md`：这 9 个任务共用的 Go 接口约定。
- `migration/judges/`：48 个独立验收场景及固定测试数据。
- `migration/workflow.json`：每个任务的测试位置、允许写入的 Go 文件、必须通过的测试名、是否检查数据竞争。
- Pith 根目录的 `go.mod/go.sum`：模块路径和固定依赖。

这些是已经准备好的输入，**不是已经完成的 Pith Go 内核**。真实候选的生成由你启动。测试准备已经过编译、错误样本拒绝及部分原 TS 对照检查；以后每个真实候选仍必须通过验收。

## 2. 先检查，不调用模型

以下命令都在 Pith 根目录运行：

```sh
cd ~/work/pith
node ../portsmith/dist/cli.js migrate --plan migration --check
```

`ready` 表示来源、任务图、接口、输出和独立测试配置齐全。它不会生成代码，不会调用 DeepSeek，也不会提交 Git。

| 部分                       | 含义                                                |
| -------------------------- | --------------------------------------------------- |
| `node`                     | 使用 Node.js 运行迁移工具                           |
| `../portsmith/dist/cli.js` | 上一级目录中，Portsmith 构建后的命令行入口          |
| `migrate`                  | 自动推进完整迁移计划的新入口                        |
| `--plan migration`         | 从当前 Pith 目录下的 migration 读取计划与工作流配置 |
| `--check`                  | 只检查准备情况，不开始执行                          |

新机器或 Portsmith 源码更新后，先在 `~/work/portsmith` 执行 `npm ci` 和 `npm run build`，再回 Pith。需要 Node.js ≥22.19、Go ≥1.24；race 检查还需要可用的 C 编译器（macOS 通常来自 Command Line Tools）。固定源码缺失时，按 Pith migration README 的来源恢复步骤补齐。

## 3. 正式启动：你只需要这条命令

```sh
node ../portsmith/dist/cli.js migrate \
  --plan migration \
  --commit \
  --env-file ../omni-pi/.env \
  --max-turns 24 \
  --timeout 600
```

- `--commit`：允许自动集成并创建 Git 提交。首次运行会先提交已有的迁移准备文件，此后每完成一个模块提交一次。**不会 push。**
- `--env-file`：显式复用之前的模型配置。支持 `PORTSMITH_BASE_URL/MODEL/API_KEY` 和原来的 `OMNI_*`；前一组优先，环境变量优先于文件。
- `--max-turns 24`：每次生成或修复最多 24 个模型循环，不是迁移 24 个模块。
- `--timeout 600`：每次生成或修复最多 600 秒，不是整批只运行十分钟。
- 每个模块每次启动默认最多生成/修复 3 次，可用 `--max-attempts 5` 改成 5 次（允许 1–10）。

需要的 Go 依赖已在这台机器下载。新机器若缓存没有这些依赖，可在正式命令后加 `--allow-download`，允许验证时下载固定版本。工具不会替模型升级依赖。

真实执行会将选定源码发送到配置的模型并产生 API 用量。执行前，先在本机确认 `.env` 仍指向你想使用的 DeepSeek 模型；不需要把密钥贴出来。

## 4. 工具内部自动做什么

```text
读取计划、接口和独立测试
         ↓
按依赖选择下一个模块
         ↓
冻结本次输入，带入前面已验收的 Go 代码
         ↓
调用模型生成 / 修复
         ↓
编译 → 候选自测 → 累计独立测试 → 适用的 race 检查
         │
         ├─ 失败：把诊断交回模型，有限次数重试
         ↓ 通过
将本模块的代码和独立测试纳入 Pith
         ↓
在 Pith 实际目录再跑累计集成测试
         ↓ 通过
创建该模块的 Git 提交
         ↓
自动进入下一个模块
```

模型只能写当前任务的明确输出文件及差异说明，不能修改前置实现、依赖清单或独立测试。每个必需的独立测试都必须实际运行并通过；编译通过或模型自测通过不够。

`--commit` 不会把无关修改夹进提交。初次准备提交的范围由 workflow.json 的 bootstrap 明确列出；遇到其他未提交修改会停止并列出路径。开始执行后要求工作区干净，集成恢复只允许本次事务记录的文件。

## 5. 停下来之后怎么办

正常的模型超时、轮数用尽或行为验证失败，会在限额内继续修复。达到本次重试上限、模型连接报错或你按 Ctrl-C 后，候选与进度保留。

**下次重跑第 3 节同一条命令。** 已完成且内容仍匹配的模块会跳过。提交已成功但进度尚未写入时，会识别该提交，不重复提交或重复生成。

| 停止原因                      | 处理                                                                       |
| ----------------------------- | -------------------------------------------------------------------------- |
| 模型密钥、额度或网络错误      | 修正本机配置/服务问题，然后重跑                                            |
| 达到修复次数上限              | 看 verification.json 和 last-run.json；可以继续重跑，或先检查接口/实现问题 |
| 缺少 Go 依赖                  | 新机器用 --allow-download，保持冻结的 go.mod/go.sum 不变                   |
| race 编译环境缺失             | 安装/修复系统编译工具，不要跳过已要求的 race 检查                          |
| 有无关工作区修改              | 自行整理这些修改后继续；工具不自动覆盖或提交它们                           |
| 集成测试或 Git 提交失败       | 已写入文件及事务记录保留；先看 integration-tests.json 或 Git 错误，再重跑  |
| 计划、API、独立测试或依赖变了 | 旧证据不能沿用；需审查并重建相关任务和流水线记录，不应盲删进度跳过检查     |
| 提示 .lock 已存在             | 先确认没有旧迁移进程在运行；若确为异常退出，再清理对应锁文件               |

如果只是想先完成一个正式模块，在第 3 节命令末尾加 `--max-units 1`。它仍是正式迁移、仍然验证和提交；达到限额后停止，下次启动继续下一个模块。

## 6. 去哪里看结果

正式验收后的 Go 文件直接出现在 Pith 的目标包，例如 `internal/eventstream/`、`ai/`、`agent/`。独立测试会和包一起纳入 Git。`migration/results/` 保存每模块的验证记录及模型提供的差异说明。

运行过程保存在 Pith 的 `.portsmith/`，被 Git 忽略：

```text
.portsmith/
├── migrate.json                 整批进度、已提交模块、待恢复事务及错误
└── tasks/
    └── P01-eventstream/
        ├── task.json            本任务冻结信息
        ├── references/          上游参考源码
        ├── candidate/           当前 Go 候选（包含只读前置源码）
        ├── judge/               累计独立测试快照
        ├── run-*.jsonl          模型运行记录
        ├── last-run.json        最近一次模型结果
        ├── verification.json    最近一次候选验证结果
        └── integration-tests.json  实际项目的集成测试结果
```

看已经产生的提交：

```sh
git log --oneline -12
```

流水线输出 `complete` 表示当前计划的全部模块已通过自动验收并提交。它不表示 Pi 所有功能已移植，也不表示真实 DeepSeek 服务已经做过冒烟测试。后者在最终 Go CLI 可用后单独执行，不把非确定性回答混进默认测试。

## 7. 以前那些命令还要手动跑吗

**正常推进 Pith 不需要。** 它们保留给调试或其他手动迁移任务：

| 命令      | 单步作用                                 |
| --------- | ---------------------------------------- |
| `next`    | 查询依赖满足的任务；不会开始执行         |
| `prepare` | 准备一个任务；单独使用不自动带入前置代码 |
| `run`     | 生成或修复一个候选；单独使用不自动验证   |
| `verify`  | 验证一个候选                             |
| `accept`  | 导出一个候选；单独使用不集成、不提交     |
| `status`  | 查询单任务或计划状态                     |

`migrate` 将这些阶段的底层能力接起来，并补上累计代码、事务恢复、实际项目测试和 Git 提交。旧的 `next/status` 按验证记录展示任务；自动执行以 `migrate.json` 中的已集成提交记录为准。

`--example event-stream` 和 `npm run demo` 都不是现在的操作入口。你要运行的是 **migrate --plan migration --commit**。
